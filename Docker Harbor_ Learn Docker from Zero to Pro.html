L1

What is Docker?

About 10 minutes. No installs yet.

By the end you can explain in one sentence what Docker does and which problem it solves.

Explain like I’m 5

Imagine you bake perfect cookies at home. You give the recipe to your friend, but their cookies come out flat. Their oven is different, their flour is different, they forgot the sugar.

Now imagine you could put your whole kitchen (oven, flour, sugar, the recipe, even your spoon) into a magic lunchbox. Your friend opens the lunchbox anywhere and the cookies come out exactly like yours. Every time.

Docker is that magic lunchbox for computer programs. The lunchbox is called a container.

The engineer’s view

Docker is a tool for packaging an application together with its runtime, libraries, system tools and settings into a standard unit called a container image. When you run that image, you get a container: an isolated process on your machine that sees only its own files, network and processes.

Why teams use it:

  • Consistency. The same image runs on a developer laptop, a CI server and production.
  • Isolation. Two apps that need different versions of Node or Python can sit side by side without fighting.
  • Speed. Containers start in about a second because they don’t boot a whole operating system.
  • Easy onboarding. A new teammate runs one command instead of following a 40-step setup guide.

The name comes from shipping: before standard steel shipping containers, dock workers loaded sacks, barrels and crates one by one. Standard boxes meant any crane, ship or truck could handle any cargo. Docker does the same for software.

Hands-on: spot the problem

No computer needed yet. Think about a project you have worked on (or imagine a website).

  1. Write down everything that must be installed for it to run: language, version, database, libraries, environment settings.
  2. Count the items. Every one of them is something that can be different on another computer.
  3. Circle the items that Docker would put “inside the lunchbox”.
Show an example answer

A small web shop might need: Node.js 20, npm packages, PostgreSQL 16, a DATABASE_URL setting, ImageMagick for photo resizing, and the right timezone. Everything except your secret passwords can go inside the container image. The database usually runs in its own separate container (you’ll do that in lesson 12).

Remember

  • A container is a lunchbox holding an app plus everything it needs.
  • Docker fixes “it works on my machine” by shipping the machine’s setup with the app.

L2

Containers vs virtual machines

About 12 minutes.

You’ll understand why containers are lighter and faster than virtual machines, and when you might still want a VM.

Explain like I’m 5

A virtual machine is like building a whole new house for every family: new walls, new roof, new plumbing, new kitchen. It works, but it takes a long time and uses a lot of land.

A container is like an apartment in one big building. Every family has their own locked front door and their own rooms, but they all share the same foundation, water pipes and electricity. Much faster to move in, and many more families fit on the same land.

The engineer’s view

A virtual machine emulates hardware through a hypervisor (VMware, Hyper-V, KVM, VirtualBox). Each VM boots its own complete operating system kernel.

A container is just a normal process on the host, fenced off using Linux kernel features:

  • Namespaces control what a process can see: its own process list (PID), network, mount points, hostname, users.
  • cgroups (control groups) control what a process can use: CPU, memory, disk I/O.
  • Union filesystems (like OverlayFS) stack read-only image layers with a thin writable layer on top.
Virtual machineContainer
IsolationVery strong (separate kernel)Strong, but shares the host kernel
SizeGigabytesMegabytes
StartupTens of seconds to minutesUnder a second, usually
Run a different OS kernel?Yes (Windows on Linux, etc.)No, uses the host’s kernel
Best forStrong multi-tenant isolation, different OSesPackaging and shipping apps, microservices

On Mac and Windows, Docker Desktop quietly runs a tiny Linux VM and puts your containers inside it, because Linux containers need a Linux kernel. You rarely notice it.

Hands-on: feel the difference (after lesson 3)

Come back here once Docker is installed. Time how long a container takes to start:

$ time docker run --rm alpine echo "hello from a container"
hello from a container
real    0m0.62s
  1. Run the command twice. The first time downloads the alpine image (about 3 MB). The second run is the true startup time.
  2. Compare with how long it takes your laptop, or any VM you’ve used, to boot.

On Windows PowerShell use Measure-Command { docker run --rm alpine echo hi } instead of time.

Remember

  • VMs = separate houses with their own OS. Containers = apartments sharing one kernel.
  • Namespaces hide things; cgroups limit things.
  • Containers are smaller and faster; VMs give stronger isolation.

About 20 minutes, mostly waiting for downloads.

Docker running on your computer, and your very first container saying hello.

Explain like I’m 5

Before you can play with LEGO you need the LEGO box. Installing Docker is getting the box. Then we’ll build our first tiny thing: a robot that just waves and says “Hello!”.

Installing

L4

Images & containers

About 15 minutes. The most important idea in the whole course.

You’ll never mix up an image and a container again.

Explain like I’m 5

Think of a cookie cutter shaped like a star. The cutter is the image. It never changes and you can’t eat it.

Every time you press it into dough, you get a cookie. That cookie is a container. You can make one cookie or a hundred from the same cutter. You can add sprinkles to one cookie and it doesn’t change the cutter or the other cookies. And when you eat a cookie, the cutter is still there to make more.

The engineer’s view
ImageContainer
What it isA read-only package: filesystem + metadata (what command to run, env vars, ports)A running (or stopped) instance of an image, with a writable layer on top
Like…A class, a recipe, a cookie cutterAn object, a cake, a cookie
List themdocker imagesdocker ps -a
Deletedocker rmi IMAGEdocker rm CONTAINER

Image names look like registry/namespace/repository:tag. Most parts are optional:

  • nginx means docker.io/library/nginx:latest
  • nginx:1.27-alpine picks a version and a smaller Alpine-based variant
  • ghcr.io/acme/shop-api:2.3.1 is a company image on GitHub’s registry

The latest tag doesn’t mean “newest”. It’s just the default name when no tag is given. In real projects, always pin a version like nginx:1.27.

Hands-on: one cutter, three cookies
  1. Download an image without running it: 
    $ docker pull nginx:1.27-alpine
$ docker images
REPOSITORY   TAG           IMAGE ID       SIZE
nginx        1.27-alpine   4a1c2f…        48MB
  2. Start three containers from the same image. -d means “detached”: run in the background. 
    $ docker run -d --name web1 nginx:1.27-alpine
$ docker run -d --name web2 nginx:1.27-alpine
$ docker run -d --name web3 nginx:1.27-alpine
$ docker ps
  3. Add “sprinkles” to only one container: 
    $ docker exec web3 sh -c "echo sprinkles > /sprinkles.txt"
$ docker exec web3 cat /sprinkles.txt
sprinkles
$ docker exec web1 cat /sprinkles.txt
cat: can't open '/sprinkles.txt': No such file or directory
  4. Clean up: 
    $ docker rm -f web1 web2 web3
Why did web1 not have the file?

Each container gets its own private writable layer. Writing in web3 only changes web3’s layer. The image underneath is read-only and shared, so web1 never sees it. And when you delete web3, the sprinkles are gone forever (lesson 10 shows how to keep data).

Remember

  • Image = cookie cutter (read-only). Container = cookie (running copy with its own changes).
  • Always pin image tags; don’t trust latest.
  • Deleting a container deletes whatever was written inside it.

L5

How Docker works inside

About 12 minutes.

You can name the three big pieces of Docker (client, daemon, registry) and say what each one does.

Explain like I’m 5

Think of a restaurant. You tell the waiter what you want: that’s the Docker client (the docker command you type). The waiter takes your order to the kitchen, where the chef does all the real cooking: that’s the Docker daemon. If the kitchen runs out of an ingredient, someone fetches it from the supermarket: that’s the registry, like Docker Hub.

The engineer’s view
  • Docker client (docker CLI): turns your commands into REST API calls.
  • Docker daemon (dockerd): a background service that builds images and manages containers, networks and volumes. It listens on a Unix socket (/var/run/docker.sock) or a named pipe on Windows.
  • containerd and runc: under the daemon, containerd manages container lifecycles and runc actually creates the isolated process using namespaces and cgroups. These follow the open OCI (Open Container Initiative) standards, which is why images built with Docker also run in Kubernetes, Podman and others.
  • Registry: a server that stores and serves images. Docker Hub is the default.

Because client and daemon talk over an API, the client can even control a daemon on a different machine, using contexts: docker context create remote --docker "host=ssh://user@server".

Anyone who can talk to docker.sock controls the whole host. Never mount it into a container unless you completely trust that container.

Hands-on: peek behind the curtain
  1. See everything the daemon knows about itself: 
    $ docker info
Containers: 0  Running: 0  Paused: 0  Stopped: 0
Images: 3
Storage Driver: overlay2
Cgroup Version: 2
Kernel Version: 6.x…
  2. See how much disk Docker is using: 
    $ docker system df
  3. Watch live events. Open a second terminal, run docker run --rm alpine echo hi there, and watch the first terminal: 
    $ docker events
container create …  container start …  container die …  container destroy …
    Press Ctrl+C to stop.

Remember

  • Client (waiter) → Daemon (kitchen) → Registry (supermarket).
  • Docker images follow the OCI standard and run on any compatible runtime.
  • Access to the Docker socket = full control of the machine.

Everyday container commands

About 25 minutes. Lots of typing.

You can start, stop, inspect, enter, read logs from, and clean up containers without looking anything up.

Explain like I’m 5

A container is like a toy robot. You can switch it on (start), switch it off (stop), freeze it mid-dance (pause), listen to what it says (logs), open its hatch and look inside (exec), and finally put it in the recycling bin (remove).

The commands you’ll use every day
CommandWhat it does
docker run -d --name NAME IMAGECreate and start in the background with a friendly name
docker run --rm -it IMAGE shInteractive throwaway container, deleted on exit
docker ps / docker ps -aList running / all containers
docker logs -f NAMEShow output and keep following it (--tail 50 for the last 50 lines)
docker exec -it NAME shOpen a shell inside a running container
docker stop NAMEPolitely ask it to stop (SIGTERM, then SIGKILL after 10s)
docker start NAME / restartStart a stopped container / stop and start again
docker rm NAME (-f to force)Delete a container
docker inspect NAMEEvery detail, as JSON
docker statsLive CPU and memory use, like Task Manager
docker cp NAME:/path ./hereCopy files out of (or into) a container
docker container pruneDelete all stopped containers
docker system prune -aBig clean-up: stopped containers, unused images, networks, build cache

You only need to type enough of a container ID to be unique: docker stop 4f2 works if no other ID starts with 4f2.

A container lives only as long as its main process (PID 1). When that process ends, the container stops. That’s why docker run alpine exits at once: sh has nothing to do and no terminal attached.

Hands-on: the robot’s day
  1. Start a robot that talks every second: 
    $ docker run -d --name robot alpine sh -c "while true; do echo beep \$(date +%T); sleep 1; done"
  2. Listen to it, then press Ctrl+C (this stops following, not the robot): 
    $ docker logs -f robot
beep 10:15:01
beep 10:15:02
  3. Freeze it, check, unfreeze: 
    $ docker pause robot
$ docker ps
STATUS
Up 30 seconds (Paused)
$ docker unpause robot
  4. Open its hatch and look around: 
    $ docker exec -it robot sh
/ # ps
PID   USER     COMMAND
    1 root     sh -c while true; do echo beep…
/ # exit
    Notice the robot’s loop is PID 1. Inside the container, it’s the only thing that exists.
  5. Find its IP address with a filter on inspect: 
    $ docker inspect -f '{{.NetworkSettings.IPAddress}}' robot
172.17.0.2
  6. Stop, remove, confirm it’s gone: 
    $ docker stop robot
$ docker rm robot
$ docker ps -a
Run docker stats in one terminal while starting three robots in another. Which one uses the most CPU? Then remove them all in one line: docker rm -f $(docker ps -aq). (Careful: that removes every container.)

Remember

  • run, ps, logs, exec, stop, rm: the six you’ll use most.
  • A container stops when its main process ends.
  • --rm cleans up automatically. Use it for experiments.

L7

Your first Dockerfile

About 30 minutes.

You’ll write a Dockerfile for a small web app, build your own image, and run it.

Explain like I’m 5

So far we used cookie cutters other people made. Now we make our own. A Dockerfile is a recipe card written step by step:

“1. Start with a plain cookie base. 2. Go to the kitchen table. 3. Add chocolate chips. 4. When someone opens the box, serve the cookie.”

Docker reads the card from top to bottom and builds your cookie cutter. That’s called building an image.

The most useful instructions
InstructionMeaningKid version
FROMBase image to start fromPlain cookie dough
WORKDIRSet (and create) the working folderGo to the kitchen table
COPYCopy files from your project into the imageBring ingredients from the shelf
RUNRun a command while buildingMix the dough now
ENVSet an environment variableWrite a sticky note
EXPOSEDocument which port the app listens onLabel which window to wave from
USERWhich user runs the appWho’s allowed in the kitchen
CMDDefault command when the container startsServe the cookie
ENTRYPOINTFixed program to run; CMD becomes its default argumentsAlways serve on a plate
ARGA variable only available during buildToday’s choice of chips

RUN vs CMD: RUN happens once, at build time, and its result is saved in the image. CMD happens every time a container starts.

Exec form vs shell form: write CMD ["node", "server.js"] (JSON array) rather than CMD node server.js. The array form runs your app directly as PID 1, so it receives stop signals properly and shuts down cleanly.

Hands-on: build your own web app image

We’ll use Python, but you don’t need to know Python. Make a new empty folder called hello-docker and create these three files.

  1. app.py 
    from flask import Flask
import os, socket

app = Flask(__name__)

@app.route("/")
def hello():
    name = os.getenv("NAME", "friend")
    return f"<h1>Hello, {name}! 🐳</h1><p>Served by container {socket.gethostname()}</p>"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
  2. requirements.txt 
    flask==3.0.3
  3. Dockerfile (exactly that name, no extension): 
    # 1. start from an official, small Python image
FROM python:3.12-slim

# 2. work inside /app
WORKDIR /app

# 3. install dependencies first (better caching, see lesson 8)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 4. copy the rest of the code
COPY . .

# 5. document the port and set the start command
EXPOSE 5000
CMD ["python", "app.py"]
  4. Build it. -t gives the image a name and tag; the final . means “the build context is this folder”. 
    $ docker build -t hello-docker:1.0 .
[+] Building 12.3s (10/10) FINISHED
 => [1/5] FROM python:3.12-slim
 => [2/5] WORKDIR /app
 => [3/5] COPY requirements.txt .
 => [4/5] RUN pip install --no-cache-dir -r requirements.txt
 => [5/5] COPY . .
 => naming to docker.io/library/hello-docker:1.0
  5. Run it and open http://localhost:5000 in your browser: 
    $ docker run -d --name hello -p 5000:5000 -e NAME=Captain hello-docker:1.0
    You should see “Hello, Captain! 🐳”. (-p is explained in lesson 9; -e in lesson 14.)
  6. Clean up: docker rm -f hello

Also add a .dockerignore file so junk never gets copied into your image:

.git
__pycache__/
*.pyc
.env
.venv/
node_modules/
Change the message in app.py, rebuild as hello-docker:1.1, and run both versions at once on ports 5000 and 5001. Two versions of one app, side by side, no conflicts.
Show the solution 
$ docker build -t hello-docker:1.1 .
$ docker run -d --name v1 -p 5000:5000 hello-docker:1.0
$ docker run -d --name v2 -p 5001:5000 hello-docker:1.1

Both containers listen on port 5000 inside, but you map them to different ports on your computer.

Remember

  • Dockerfile → docker build → image → docker run → container.
  • RUN is for build time; CMD is for start time.
  • Use the JSON array form for CMD, and always add a .dockerignore.

L8

Layers & build cache

About 20 minutes.

You’ll know why builds are sometimes instant and sometimes slow, and how to order a Dockerfile so they’re fast.

Explain like I’m 5

An image is a stack of pancakes. Each line in your Dockerfile adds one pancake on top.

Docker is clever: it remembers every pancake it already made. If the recipe for a pancake hasn’t changed, it reuses the old one instead of cooking it again. But if you change pancake number 3, it must re-cook number 3 and every pancake on top of it, because they were sitting on the old one.

So put the pancakes that almost never change at the bottom, and the ones that change all the time at the top.

The engineer’s view
  • RUN, COPY and ADD create filesystem layers. Others (ENV, CMD, EXPOSE…) only add metadata.
  • Layers are content-addressed and shared. Ten images based on python:3.12-slim store that base only once on disk.
  • For COPY, the cache key includes a checksum of the copied files. For RUN, it’s the command text, so RUN apt-get update won’t notice new packages until something above it changes.
  • Deleting a file in a later layer doesn’t shrink the image; the file still lives in the earlier layer. Clean up in the same RUN:
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl \
 && rm -rf /var/lib/apt/lists/*

BuildKit cache mounts (advanced): keep a package cache between builds without baking it into the image:

# syntax=docker/dockerfile:1
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt
Hands-on: watch the cache work

Use the hello-docker folder from lesson 7.

  1. Build twice in a row. The second build shows CACHED on every step and finishes almost instantly. 
    $ docker build -t hello-docker:cache .
 => CACHED [2/5] WORKDIR /app
 => CACHED [3/5] COPY requirements.txt .
 => CACHED [4/5] RUN pip install …
  2. Edit one word in app.py and build again. Only step 5 reruns. The slow pip install stays cached.
  3. Now break it on purpose: move COPY . . above the RUN pip install line, edit app.py, build. Feel the pain as pip reinstalls. Then put it back.
  4. See the layers of your image and their sizes: 
    $ docker history hello-docker:1.0
CREATED BY                                      SIZE
CMD ["python" "app.py"]                         0B
COPY . . # buildkit                             2.1kB
RUN pip install --no-cache-dir -r requirem…     11MB
…
Install the open-source tool dive and run dive hello-docker:1.0 to explore every file in each layer.

Remember

  • Each RUN/COPY/ADD adds a layer; layers are cached and shared.
  • Change one layer → it and everything above rebuild.
  • Rarely-changing steps first, your code last. Clean up in the same RUN.

L9

Ports: opening doors

About 15 minutes.

You can make an app inside a container reachable from your browser, and fix the classic “port already in use” error.

Explain like I’m 5

A container is a house with all its doors locked. Inside, a shop is open behind door number 80, but nobody outside can get in.

Port mapping is putting a doorbell on the street (your computer’s port 8080) that is wired to that inside door (container port 80). Ring the street doorbell, and you walk right into the shop.

The engineer’s view
FlagEffect
-p 8080:80Host port 8080 on all interfaces → container port 80
-p 127.0.0.1:8080:80Only reachable from this machine (safer for dev databases)
-p 80Random free host port → container 80 (see it with docker port NAME)
-PPublish every EXPOSEd port to random host ports
-p 5353:53/udpUDP instead of TCP
  • EXPOSE in a Dockerfile is only documentation. It doesn’t open anything. -p does.
  • Your app must listen on 0.0.0.0 inside the container, not 127.0.0.1. Otherwise it only accepts connections from inside the container itself and you’ll get “connection reset”. This is the number one beginner bug.
  • Two containers can both use port 80 inside. Only host ports must be unique.

On Linux, published ports can bypass firewalls like ufw because Docker writes its own iptables rules. On servers, bind to 127.0.0.1 unless the port really should be public.

Hands-on: three doorbells
  1. Run nginx and visit http://localhost:8080: 
    $ docker run -d --name shop -p 8080:80 nginx:1.27-alpine
  2. Try to start another container on the same host port. Read the error carefully: 
    $ docker run -d --name shop2 -p 8080:80 nginx:1.27-alpine
Error … Bind for 0.0.0.0:8080 failed: port is already allocated
  3. Fix it by using a different host port: 
    $ docker rm shop2
$ docker run -d --name shop2 -p 8081:80 nginx:1.27-alpine
  4. Let Docker pick a random port and ask which one it chose: 
    $ docker run -d --name shop3 -P nginx:1.27-alpine
$ docker port shop3
80/tcp -> 0.0.0.0:55001
  5. Clean up: docker rm -f shop shop2 shop3

Remember

  • -p HOST:CONTAINER. Outside on the left, inside on the right.
  • EXPOSE documents; -p publishes.
  • Apps must listen on 0.0.0.0 inside containers.
Next: Volumes
L10

Volumes: data that stays

About 25 minutes.

You can keep database data safe when containers are deleted, and live-edit code inside a container.

Explain like I’m 5

Remember: when you throw away a cookie, its sprinkles go too. That’s bad if the cookie was your diary!

A volume is a special toy box that sits outside the container. The container can put things in it and take things out, but when the container is thrown away, the toy box stays. A new container can open the same toy box and find everything still there.

Three kinds of storage
TypeSyntaxWhere data livesUse it for
Named volume-v pgdata:/var/lib/postgresql/dataManaged by DockerDatabases, anything to persist in production
Bind mount-v "$(pwd)":/appA folder you choose on the hostLive code editing in development, config files
tmpfs--tmpfs /tmpMemory only, gone on stopSecrets, scratch files you never want on disk

The longer --mount syntax is clearer and makes fewer silent mistakes:

$ docker run --mount type=volume,source=pgdata,target=/var/lib/postgresql/data postgres:16
$ docker run --mount type=bind,source="$(pwd)",target=/app,readonly my-app

With -v, a typo in a host path silently creates an empty folder. --mount gives an error instead.

Volume commands: docker volume ls, create, inspect, rm, prune.

Back up a volume by mounting it into a throwaway container together with a bind mount:
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar czf /backup/pgdata.tgz -C /data .

Hands-on: the diary that survives
  1. Create a volume and write a diary entry into it from a container: 
    $ docker volume create diary
$ docker run --rm -v diary:/notes alpine sh -c "echo 'Day 1: learned volumes' >> /notes/diary.txt"
  2. That container is already gone (--rm). Read the diary from a brand-new container: 
    $ docker run --rm -v diary:/notes alpine cat /notes/diary.txt
Day 1: learned volumes
  3. Real-world version: a PostgreSQL database that keeps its data. 
    $ docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16-alpine
$ docker exec -it db psql -U postgres -c "CREATE TABLE pets(name text); INSERT INTO pets VALUES ('Rex');"
$ docker rm -f db
$ docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16-alpine
$ docker exec -it db psql -U postgres -c "SELECT * FROM pets;"

    Wait a few seconds after starting before running psql, so the database is ready.
  4. Bind mount for live editing. Make a folder with an index.html, then: 
    $ docker run -d --name live -p 8080:80 -v "$(pwd)":/usr/share/nginx/html:ro nginx:1.27-alpine

Networks: containers talking

About 20 minutes.

Your app container can reach your database container by name.

Explain like I’m 5

Containers are like kids in different rooms. To talk, they need walkie-talkies on the same channel. A Docker network is that channel.

Even better: on your own channel, you don’t need to remember phone numbers. You just say “Hey, db!” and the right kid answers. That’s Docker’s built-in name lookup (DNS).

Network drivers
DriverWhat it isWhen to use
bridge (default)Private network on one hostAlmost always. Create your own: the default bridge has no name-based DNS.
hostContainer shares the host’s network directly, no isolationMax network performance, Linux only
noneNo network at allBatch jobs that must never reach the internet
overlayOne network spanning many hostsDocker Swarm (lesson 20)
macvlanContainer gets its own MAC/IP on your physical LANLegacy apps that expect to be a “real” machine

Inside a container, localhost means that container, not your computer. To reach a service on your host machine from a container, use host.docker.internal (built into Docker Desktop; on Linux add --add-host=host.docker.internal:host-gateway).

Hands-on: walkie-talkie channel
  1. Create a network and start a Redis server on it: 
    $ docker network create shopnet
$ docker run -d --name cache --network shopnet redis:7-alpine
  2. From another container on the same network, talk to it by name: 
    $ docker run --rm -it --network shopnet redis:7-alpine redis-cli -h cache ping
PONG
$ docker run --rm -it --network shopnet redis:7-alpine redis-cli -h cache set greeting "hello neighbour"
$ docker run --rm -it --network shopnet redis:7-alpine redis-cli -h cache get greeting
"hello neighbour"
  3. Try from a container not on the network: 
    $ docker run --rm -it redis:7-alpine redis-cli -h cache ping
Could not connect to Redis at cache:6379: Name does not resolve
  4. See who’s on the channel: 
    $ docker network inspect shopnet -f '{{range .Containers}}{{.Name}} {{end}}'
  5. Connect an existing container later with docker network connect shopnet NAME. Clean up: docker rm -f cache and docker network rm shopnet.

Notice we never published Redis with -p. Containers on the same network talk directly. Only publish ports for things humans or the outside world need to reach.

Remember

  • Make your own bridge network; then containers find each other by name.
  • localhost inside a container is the container itself.
  • Internal services (databases, caches) usually need no -p at all.

Docker Compose: the conductor

About 35 minutes. A big one, and the one you’ll use most at work.

You can describe a whole multi-container app in one file and start it with one command.

Explain like I’m 5

An orchestra has violins, drums and a trumpet. Telling each musician separately when to play would be exhausting. So there’s a conductor holding one sheet of music for everybody.

Docker Compose is the conductor. The sheet of music is a file called compose.yaml. You say “docker compose up” and the whole orchestra (website, database, cache) starts playing together.

Anatomy of compose.yaml
services:
  web:                       # service name = DNS name on the network
    image: nginx:1.27-alpine
    ports:
      - "8080:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - api

  api:
    build: ./api             # build from a Dockerfile in ./api
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy   # wait until db is truly ready

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 10

volumes:
  dbdata:
CommandWhat it does
docker compose up -dBuild if needed, create and start everything in the background
docker compose up -d --buildForce a rebuild of images first
docker compose psStatus of this project’s services
docker compose logs -f apiFollow logs of one service
docker compose exec db psql -U appRun a command in a running service
docker compose downStop and remove containers and the network (volumes kept)
docker compose down -v…and delete volumes too. Data gone!
docker compose configShow the final merged file. Great for spotting typos.
docker compose watchSync or rebuild automatically when your code changes

The old command was docker-compose (with a hyphen) and files were named docker-compose.yml. Modern Docker uses docker compose (a space) and prefers compose.yaml, but still reads the old name. The version: line at the top of old files is no longer needed.

depends_on alone only waits for the container to start, not for the database to be ready. Use condition: service_healthy with a healthcheck, as above.

Hands-on: a visit counter in one command

Registries, tags & sharing images

About 20 minutes. You’ll need a free Docker Hub account.

You can tag an image properly, push it to a registry and pull it anywhere.

Explain like I’m 5

A registry is a library for cookie cutters. You make a great cutter at home, put a label on it (that’s a tag, like “star-cutter, version 2”), and give it to the library (push). Anyone with a library card can borrow a copy (pull), from any town in the world.

The engineer’s view

Popular registries: Docker Hub (default), GitHub Container Registry (ghcr.io), AWS ECR, Google Artifact Registry, Azure ACR, GitLab, and self-hosted Harbor or the basic registry:2 image.

Tagging strategy used by most teams:

  • Semantic version tags: 1.4.0, plus moving tags 1.4 and 1.
  • Git commit SHA: shop:3f9c2ab, so you know exactly which code is running.
  • Never deploy latest to production. You can’t tell what it is or roll back reliably.

Digests: every image also has an unchangeable fingerprint like nginx@sha256:6af7…. A tag can be moved to a new image; a digest can’t. Pin by digest when you need guaranteed reproducibility.

Multi-platform images: Apple Silicon Macs are arm64, most cloud servers are amd64. Build for both at once:

$ docker buildx build --platform linux/amd64,linux/arm64 -t you/shop:1.4.0 --push .
Hands-on: publish your app

Replace YOURNAME with your Docker Hub username.

  1. Log in: 
    $ docker login
Login Succeeded
  2. Give your lesson-7 image a registry name. Tagging doesn’t copy anything; it’s just another label on the same image ID. 
    $ docker tag hello-docker:1.0 YOURNAME/hello-docker:1.0
$ docker tag hello-docker:1.0 YOURNAME/hello-docker:1
$ docker images | grep hello-docker
  3. Push both tags. Notice the second push says “Layer already exists”. 
    $ docker push YOURNAME/hello-docker:1.0
$ docker push YOURNAME/hello-docker:1
  4. Prove it works from scratch: delete your local copies and run straight from the registry. 
    $ docker rmi YOURNAME/hello-docker:1.0 YOURNAME/hello-docker:1 hello-docker:1.0
$ docker run -d -p 5000:5000 YOURNAME/hello-docker:1.0
Run your own private registry locally: docker run -d -p 5001:5000 --name registry registry:2, tag your image as localhost:5001/hello-docker:1.0, and push it there.

Remember

  • tag → push → pull. The image name decides which registry it goes to.
  • Use version or commit-SHA tags, not latest.
  • Digests (@sha256:…) never change; tags can.

Environment variables & configuration

About 20 minutes.

One image that runs in development, testing and production just by changing its settings, without ever putting passwords inside it.

Explain like I’m 5

Your toy robot is the same robot whether you play at home or at grandma’s. But at grandma’s, you whisper different instructions: “Talk quietly, grandma is sleeping.”

Environment variables are those whispered instructions. The robot (image) stays exactly the same. Only the whispers change. And secret whispers, like the password to your treasure chest, are never written on the robot itself.

All the ways to pass settings
WayExampleGood for
Dockerfile ENVENV PORT=8080Safe defaults baked into the image
-e flagdocker run -e LOG_LEVEL=debug appQuick overrides
--env-filedocker run --env-file .env appMany variables at once
Compose environment: / env_file:see belowMulti-service projects
Compose variable substitutionimage: shop:${TAG:-latest}Reusing one compose file across environments
Build ARGdocker build --build-arg PY=3.12 .Build-time choices. Never secrets!
SecretsCompose secrets:, Swarm/K8s secretsPasswords, API keys, certificates
services:
  api:
    image: shop-api:${TAG:-dev}
    env_file: .env                # non-secret settings
    environment:
      LOG_LEVEL: ${LOG_LEVEL:-info}
      DB_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./secrets/db_password.txt   # mounted as a file, not an env var

Anything in ENV or ARG is saved in the image. Run docker history or docker inspect and anyone can read it. Never put passwords there, and add .env to both .gitignore and .dockerignore.

Secrets mounted as files (under /run/secrets/) are safer than environment variables, which can leak into logs, crash reports and docker inspect. Many official images support a _FILE suffix for this, like POSTGRES_PASSWORD_FILE.

For secrets needed during the build (like a private package token), use BuildKit secret mounts. They’re never stored in a layer:

# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci
$ docker build --secret id=npm_token,src=./npm_token.txt .
Hands-on: whisper to the robot
  1. Run the lesson-7 app three ways: 
    $ docker run --rm -d -p 5000:5000 --name a hello-docker:1.0
$ docker run --rm -d -p 5001:5000 --name b -e NAME=Grandma hello-docker:1.0
$ printf "NAME=Production Team\n" > prod.env
$ docker run --rm -d -p 5002:5000 --name c --env-file prod.env hello-docker:1.0
    Visit ports 5000, 5001 and 5002. Same image, three greetings.
  2. See what anyone could read from a container’s environment: 
    $ docker inspect b -f '{{json .Config.Env}}'
["NAME=Grandma","PATH=…","PYTHON_VERSION=3.12…"]
    This is why real passwords belong in secrets, not plain env vars.
  3. Clean up: docker rm -f a b c

Remember

  • Same image everywhere; only the configuration changes.
  • ENV/ARG values are visible in the image. No secrets there.
  • Use secret files and BuildKit secret mounts for anything sensitive.

Multi-stage builds: travel light

About 25 minutes.

You’ll shrink an image from around a gigabyte to a few megabytes by leaving the tools behind.

Explain like I’m 5

To build a sandcastle you need buckets, spades, water and a big mess. But when you show the castle to your friends, you don’t bring the buckets and spades. You bring only the castle.

A multi-stage build uses a big messy workshop to make your program, then copies only the finished program into a tiny clean box.

The engineer’s view

Each FROM starts a new stage. Name stages with AS, and copy artifacts between them. Only the last stage becomes the image (unless you choose one with --target).

Benefits: much smaller images, faster pulls and deploys, and a smaller attack surface (no compilers or shells for an attacker to use).

Example: Node.js frontend served by nginx

# ---- build stage ----
FROM node:20-alpine AS build
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build            # outputs static files to /src/dist

# ---- runtime stage ----
FROM nginx:1.27-alpine
COPY --from=build /src/dist /usr/share/nginx/html
EXPOSE 80

Choosing a base image

BaseTypical sizeNotes
ubuntu, debian75–120 MBFamiliar, lots of tools, bigger
*-slim~50–150 MB with runtimeDebian minus extras. Great default for Python/Node.
alpine~5 MBTiny, uses musl libc, which occasionally breaks compiled Python wheels
distroless2–20 MBOnly your runtime, no shell or package manager. Very secure, harder to debug.
scratch0 MBCompletely empty. For static binaries (Go, Rust).
Hands-on: from 800 MB to 10 MB

We’ll use Go because it compiles to a single file. You don’t need Go installed; Docker brings it.

  1. Create main.go: 
    package main

import (
	"fmt"
	"net/http"
)

func main() {
	http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "Tiny but mighty 🐜")
	})
	http.ListenAndServe(":8080", nil)
}
  2. First, the “fat” way. Save as Dockerfile.fat: 
    FROM golang:1.23
WORKDIR /src
COPY main.go .
RUN go mod init tiny && go build -o /app main.go
CMD ["/app"]
  3. Now the multi-stage way. Save as Dockerfile: 
    FROM golang:1.23 AS builder
WORKDIR /src
COPY main.go .
RUN go mod init tiny && CGO_ENABLED=0 go build -ldflags="-s -w" -o /app main.go

FROM scratch
COPY --from=builder /app /app
EXPOSE 8080
ENTRYPOINT ["/app"]
  4. Build both and compare: 
    $ docker build -f Dockerfile.fat -t tiny:fat .
$ docker build -t tiny:slim .
$ docker images tiny
REPOSITORY  TAG   SIZE
tiny        fat   ~850MB
tiny        slim  ~5MB
  5. Run the slim one: docker run --rm -p 8080:8080 tiny:slim and open http://localhost:8080.
Why CGO_ENABLED=0?

It makes Go build a fully static binary that doesn’t need any system C libraries. scratch has nothing in it, not even libc, so a dynamically linked program would fail with a confusing “no such file or directory” error.

Apply a multi-stage build to your lesson-7 Python app: install dependencies with pip install --prefix=/install in a builder stage, then COPY --from=builder /install /usr/local into a fresh python:3.12-slim.

Remember

  • Build in a big stage, ship from a small one.
  • COPY --from=STAGE picks exactly what to keep.
  • Smaller images = faster deploys and fewer security holes.

Health checks, restarts & resource limits

About 25 minutes.

Containers that notice when they’re sick, get back up after a crash, and can’t eat the whole computer.

Explain like I’m 5

A health check is a nurse who visits every few seconds and asks, “Are you okay?” If you don’t answer three times in a row, the nurse marks you as unhealthy.

A restart policy is a rule like: “If the robot falls over, stand it back up.”

Resource limits are like telling a hungry kid: “You can have two slices of pizza, not the whole pizza,” so everyone else gets some too.

The engineer’s view

Health checks

HEALTHCHECK --interval=10s --timeout=3s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:5000/health || exit 1

Exit code 0 means healthy, 1 means unhealthy. The image must contain the tool you use (curl, wget, or a small script). Status shows in docker ps. Compose can wait on it with condition: service_healthy, and orchestrators replace unhealthy containers automatically.

Restart policies

PolicyBehaviour
no (default)Never restart
on-failure[:5]Restart only on non-zero exit, optionally max 5 tries
alwaysAlways restart, including when the Docker daemon starts
unless-stoppedLike always, except if you stopped it yourself. A good default for servers.

Resource limits

$ docker run -d --memory=256m --cpus=0.5 --pids-limit=100 my-app

If a container goes over its memory limit, the kernel kills it (exit code 137, “OOMKilled”). In Compose:

services:
  api:
    image: shop-api:2.0
    restart: unless-stopped
    deploy:
      resources:
        limits:
          cpus: "0.50"
          memory: 256M

Graceful shutdown

docker stop sends SIGTERM, waits 10 seconds, then sends SIGKILL. Your app should catch SIGTERM, finish current requests and close database connections. If PID 1 is a shell script, signals may never reach your app: use the exec form of CMD, or exec in your entrypoint script, or run with --init to add a tiny init process.

Hands-on: nurse, bouncer and pizza rules
  1. A container with a health check you can make fail on purpose: 
    $ docker run -d --name patient \
    --health-cmd "test -f /tmp/ok" --health-interval 3s --health-retries 2 \
    alpine sh -c "touch /tmp/ok; sleep 3600"
$ docker ps      # wait a few seconds: (healthy)
$ docker exec patient rm /tmp/ok
$ docker ps      # after ~6 seconds: (unhealthy)
  2. A container that crashes, with a restart policy: 
    $ docker run -d --name phoenix --restart on-failure:3 alpine sh -c "echo rising; sleep 2; exit 1"
$ docker ps -a   # watch STATUS: Restarting (1)…
$ docker inspect phoenix -f '{{.RestartCount}}'
3
  3. Hit a memory limit on purpose: 
    $ docker run --name hungry --memory=20m alpine sh -c "dd if=/dev/zero bs=1M count=100 | tail > /dev/null"
$ docker inspect hungry -f '{{.State.OOMKilled}} {{.State.ExitCode}}'
true 137
  4. Clean up: docker rm -f patient phoenix hungry

Remember

  • HEALTHCHECK tells Docker if the app actually works, not just if it’s running.
  • --restart unless-stopped for long-running services.
  • Always set memory limits in production; exit code 137 usually means out of memory.

Security best practices

About 30 minutes.

You’ll harden an image and a container using the checklist real teams use.

Explain like I’m 5

Your container is a castle. Good castles have many walls, not one. If a bad guy gets over the first wall, there’s another one, and another.

Rules for a safe castle: don’t give everyone the king’s keys (don’t run as root). Don’t leave ladders lying around (remove tools you don’t need). Lock the doors you don’t use. Check the bricks for cracks before building (scan images). And never write the treasure-chest code on the castle wall (secrets).

The hardened Dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim@sha256:<digest>   # pinned, trusted, minimal

# create an unprivileged user
RUN groupadd -r app && useradd -r -g app -u 10001 app

WORKDIR /app
COPY --chown=app:app requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY --chown=app:app . .

USER 10001                                 # never run as root
EXPOSE 5000
HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:5000')"
CMD ["python", "app.py"]

The hardened run command

$ docker run -d --name app \
    --read-only --tmpfs /tmp \
    --cap-drop ALL \
    --security-opt no-new-privileges \
    --memory 256m --cpus 0.5 --pids-limit 100 \
    -p 127.0.0.1:5000:5000 \
    my-app:1.0
FlagWhy
--read-onlyAttackers can’t drop files or modify the app
--cap-drop ALLRemoves special root powers (add back only what’s needed with --cap-add)
no-new-privilegesBlocks gaining root through setuid programs
--pids-limitStops “fork bombs”

Never use --privileged or mount /var/run/docker.sock unless you fully understand that it hands over the whole host.

Scanning

Scan images in development and in CI with Docker Scout (docker scout cves my-app:1.0), Trivy (trivy image my-app:1.0) or Grype. Rebuild regularly so you pick up patched base images. Use Hadolint to lint Dockerfiles and generate an SBOM (software bill of materials) so you know exactly what’s inside.

Rootless Docker and user-namespace remapping go one step further: even “root” in the container maps to an unprivileged user on the host.

Hands-on: who am I?
  1. See the default: root. 
    $ docker run --rm alpine id
uid=0(root) gid=0(root)
  2. Run as a nobody: 
    $ docker run --rm --user 65534 alpine id
uid=65534(nobody) gid=65534(nobody)
$ docker run --rm --user 65534 alpine touch /etc/hacked
touch: /etc/hacked: Permission denied
  3. Read-only filesystem: 
    $ docker run --rm --read-only alpine touch /hello
touch: /hello: Read-only file system
$ docker run --rm --read-only --tmpfs /tmp alpine touch /tmp/hello && echo "tmp is fine"
  4. Scan an image (Trivy runs in a container, so nothing to install): 
    $ docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image python:3.12-slim
Total: 85 (UNKNOWN: 0, LOW: 60, MEDIUM: 18, HIGH: 6, CRITICAL: 1)
    Compare with python:3.12-alpine or a distroless image. (We mount the socket here only because we trust this official scanner and it’s a one-off.)
  5. Lint a Dockerfile: docker run --rm -i hadolint/hadolint < Dockerfile

Remember

  • Minimal, pinned base images. Scan them. Rebuild often.
  • USER non-root, --read-only, --cap-drop ALL, no-new-privileges.
  • No secrets in images. No --privileged. Guard the Docker socket.

Debugging like a detective

About 25 minutes.

A repeatable checklist for when “the container doesn’t work”.

Explain like I’m 5

When a toy stops working, a good detective doesn’t panic. They ask questions in order: Is it switched on? What was the last thing it said? Let me open it and look inside. Can it hear me? Docker gives you a magnifying glass for every one of those questions.

The detective’s toolkit
QuestionCommand
What state is it in? What exit code?docker ps -a
What did it say before dying?docker logs --tail 100 -t NAME
What exactly was it started with?docker inspect NAME (Cmd, Env, Mounts, Networks, State)
Let me look around insidedocker exec -it NAME sh (or bash)
It crashes too fast to exec intodocker run -it --entrypoint sh IMAGE
No shell in the image (distroless)docker debug NAME (Docker Desktop) or attach a toolbox: docker run -it --network container:NAME nicolaka/netshoot
Can it reach the database?docker exec NAME nc -zv db 5432 or getent hosts db
What files changed?docker diff NAME
Which step of the build broke?docker build --progress=plain --no-cache .
Is it using too much?docker stats, docker top NAME

Classic errors and fixes

SymptomUsual cause
Container exits immediatelyMain process finished or crashed. Check logs. A server must stay in the foreground.
exec format errorImage built for arm64 running on amd64 (or the reverse). Rebuild with --platform.
exec /entrypoint.sh: no such file or directory but the file existsWindows line endings (CRLF) in the script, or a missing interpreter in the image
Connection refused from the browserApp listens on 127.0.0.1 inside, or missing -p
Can’t reach another container by nameNot on the same user-defined network
Permission denied on a bind mountContainer user ID differs from the host folder’s owner
“No space left on device”Old images and build cache. docker system df, then docker system prune.
Hands-on: solve three mysteries

Each command is broken in a different way. Run it, investigate with the toolkit, and fix it before opening the solution.

  1. The vanishing server 
    $ docker run -d --name m1 python:3.12-slim python -c "print('serving…')"
$ docker ps          # where did it go?
    Solution

    docker ps -a shows “Exited (0)”. docker logs m1 shows it printed and finished. A container lives only as long as its main process. A real server needs to keep running, for example python -m http.server 8000.

  2. The locked door 
    $ docker run -d --name m2 -p 8000:8000 python:3.12-slim python -m http.server 8000 --bind 127.0.0.1
$ curl localhost:8000     # fails
    Solution

    The server binds to 127.0.0.1 inside the container, so traffic arriving from outside is rejected. Use --bind 0.0.0.0.

  3. The lonely neighbour 
    $ docker run -d --name m3db redis:7-alpine
$ docker run --rm redis:7-alpine redis-cli -h m3db ping
    Solution

    Both are on the default bridge network, which has no name lookup. Create a network and attach both: docker network create m3net, docker network connect m3net m3db, then run the client with --network m3net.

Clean up: docker rm -f m1 m2 m3db and docker network rm m3net.

Remember

  • Order: ps -a → logs → inspect → exec.
  • Exit codes are clues: 0 finished, 1 app error, 137 killed (often memory), 127 command not found.
  • Override the entrypoint to get inside images that crash instantly.

Docker in CI/CD

About 30 minutes. Needs a GitHub account.

Every time you push code, a robot builds, tests, scans and publishes your image automatically.

Explain like I’m 5

Imagine a toy factory conveyor belt. You drop your drawing of a new toy at the start. Robot arms automatically build it, a robot tests it bounces properly, a robot checks it’s safe, and at the end it’s wrapped and put on the shop shelf. You never touch it after the drawing.

That conveyor belt is CI/CD (Continuous Integration / Continuous Delivery). Docker is the box everything travels in.

A real GitHub Actions pipeline

Save this as .github/workflows/docker.yml in your repository. It builds on every push, runs tests inside the image, scans it, and pushes to GitHub Container Registry on the main branch, tagged with the commit SHA.

name: docker
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - name: Build image (with cache)
        uses: docker/build-push-action@v6
        with:
          context: .
          load: true
          tags: app:test
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Run tests inside the image
        run: docker run --rm app:test python -m pytest -q

      - name: Scan for vulnerabilities
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: app:test
          severity: CRITICAL,HIGH
          exit-code: "1"

      - name: Log in to GHCR
        if: github.ref == 'refs/heads/main'
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Push
        if: github.ref == 'refs/heads/main'
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          platforms: linux/amd64,linux/arm64
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:main
          cache-from: type=gha

Action version numbers change over time. Check each action’s page for its current release before using this in a real project.

Good habits

  • Build once, promote everywhere. Don’t rebuild for staging and production; deploy the same digest.
  • Cache layers between CI runs (type=gha, or a registry cache) to cut build times dramatically.
  • Fail the build on critical vulnerabilities.
  • Use Compose in CI to spin up a real database for integration tests: docker compose -f compose.test.yaml up --abort-on-container-exit.
Hands-on: your own conveyor belt
  1. Push your lesson-7 hello-docker folder to a new GitHub repository.
  2. Add a tiny test file test_app.py and add pytest to requirements.txt: 
    from app import app

def test_home():
    client = app.test_client()
    assert b"Hello" in client.get("/").data
  3. Add the workflow above, commit, push, and open the Actions tab on GitHub to watch the belt move.
  4. Break the test on purpose (change “Hello” to “Bye” in the test), push, and confirm the image is not pushed.
  5. Fix it, push again, and find your image under your profile’s Packages.

Remember

  • Build → test → scan → push → deploy, automatically on every change.
  • Tag images with the commit SHA; deploy the exact tested image.
  • Cache layers in CI to keep pipelines fast.

Orchestration: Swarm & Kubernetes

About 35 minutes.

You’ll understand what an orchestrator does, run a self-healing service on Docker Swarm, and see how the same ideas look in Kubernetes.

Explain like I’m 5

Compose is a conductor for one orchestra on one stage. But what if you have ten stages in ten cities, and you always want exactly five violin players playing, even if one gets sick?

An orchestrator is the boss of all the stages. You don’t say “start this violin on stage 3.” You say “I want five violins, always.” If a violinist falls asleep, the boss immediately finds a new one on another stage. That’s called self-healing, and “five, always” is called desired state.

What orchestrators do

Scheduling containers across many machines, keeping a set number of replicas, rolling updates with zero downtime and automatic rollback, load balancing and service discovery, secrets and config distribution, and scaling up or down.

Docker SwarmKubernetes
SetupBuilt into Docker: docker swarm initSeparate system (kubeadm, k3s, or managed EKS/GKE/AKS)
Learning curveGentle; uses Compose filesSteep; many concepts
EcosystemSmallHuge; the industry standard
Unit of workService → tasks (containers)Deployment → ReplicaSet → Pods
Good forSmall teams, simple clustersMost production platforms at scale

Your Docker skills transfer directly: Kubernetes runs the same OCI images you built in this course.

Hands-on: a self-healing swarm on your laptop
  1. Turn your Docker into a one-node swarm: 
    $ docker swarm init
Swarm initialized: current node (abc123) is now a manager.
  2. Create a service with three replicas behind a built-in load balancer: 
    $ docker service create --name web --replicas 3 -p 8080:80 nginx:1.27-alpine
$ docker service ps web
  3. Kill one replica and watch Swarm replace it within seconds: 
    $ docker rm -f $(docker ps -q --filter name=web | head -n 1)
$ docker service ps web
NAME      CURRENT STATE
web.1     Running 3 seconds ago
 \_ web.1 Failed 5 seconds ago   ← the one you killed
  4. Scale up, then do a zero-downtime rolling update: 
    $ docker service scale web=6
$ docker service update --image nginx:1.27 --update-parallelism 2 --update-delay 5s web
$ docker service rollback web     # changed your mind?
  5. Deploy a Compose file as a stack (uses the deploy: section): docker stack deploy -c compose.yaml mystack
  6. Clean up: docker service rm web then docker swarm leave --force
Install a local Kubernetes (Docker Desktop has a “Enable Kubernetes” checkbox, or use kind / minikube), apply deployment.yaml with kubectl apply -f deployment.yaml, delete a pod with kubectl delete pod …, and watch it come back with kubectl get pods -w.

Remember

  • Orchestrators keep desired state across many machines and heal automatically.
  • Swarm is built into Docker and easy; Kubernetes is the industry standard.
  • Pods, Deployments and Services are Kubernetes’ versions of containers, replicas and service names.

Capstone: ship a full app

2–4 hours. Uses everything.

A production-style, multi-service app: load balancer, scaled API, database and cache, all hardened and running from one command.

Requirements checklist
  1. API in any language you like, with endpoints GET / (counts visits in Redis), GET /notes and POST /notes (stored in Postgres), and GET /health. It must report its hostname so you can see load balancing.
  2. Dockerfile: multi-stage, pinned base, .dockerignore, non-root USER, HEALTHCHECK, exec-form CMD.
  3. compose.yaml: four services; two networks (frontend for proxy+api, backend marked internal: true for api+db+cache); named volume for Postgres; depends_on with service_healthy; restart policies; memory limits.
  4. Scale the API to three replicas: docker compose up -d --scale api=3. The API must not publish a host port (why? lesson 9).
  5. Config: settings from .env; the database password as a Compose secret file.
  6. Prove it works: refresh the page and see different hostnames; restart everything and see your notes survive.
  7. Ship it: CI pipeline that builds, tests, scans and pushes the API image to a registry.
Starter compose.yaml (try on your own first) 
services:
  proxy:
    image: nginx:1.27-alpine
    ports: ["8080:80"]
    volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro"]
    depends_on: [api]
    networks: [frontend]
    restart: unless-stopped

  api:
    build: ./api
    env_file: .env
    environment:
      DB_HOST: db
      REDIS_HOST: cache
      DB_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    depends_on:
      db: { condition: service_healthy }
      cache: { condition: service_started }
    networks: [frontend, backend]
    restart: unless-stopped
    deploy:
      resources:
        limits: { memory: 256M, cpus: "0.5" }

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: notes
      POSTGRES_USER: notes
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes: ["dbdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U notes"]
      interval: 5s
      retries: 10
    networks: [backend]
    restart: unless-stopped

  cache:
    image: redis:7-alpine
    networks: [backend]
    restart: unless-stopped

networks:
  frontend:
  backend:
    internal: true

volumes:
  dbdata:

secrets:
  db_password:
    file: ./secrets/db_password.txt
upstream api_pool {
    server api:5000;      # Docker DNS returns all replicas; nginx spreads requests
}
server {
    listen 80;
    location / {
        proxy_pass http://api_pool;
        proxy_set_header Host $host;
    }
}

nginx resolves api once at startup. If you scale after the proxy has started, run docker compose restart proxy.
